# ESP32 智能风扇架构

状态：面向实现的设计方案；ESP-005 的消抖逻辑与 ESP-006 的手动控制器已实现并通过主机测试，尚未接入板端固件。依据：已讨论的 MVP 计划与套件商品图。文中的接口、周期、异常策略是本项目的设计默认值；GPIO、板型和驱动参数仍待实物确认。

## 1. 目标与范围

实现一个可独立运行的桌面小风扇：按键和红外控制 → 同一 Wi-Fi 下网页控制 → 温度自动控制。ESP32 既是设备控制器，也是网页和 HTTP API 的提供者。电脑只用于开发、烧录和串口调试，不是运行时服务器。

MVP 不包含云服务器、数据库、用户账户、手机原生 App、MQTT、OTA、跨公网控制或调速。网页仅在可信局域网使用，不开放路由器端口映射。未来若增加公网访问，必须单独设计认证和安全传输。

## 2. 部署结构

- 手机浏览器通过家中 Wi-Fi 路由器访问 ESP32 的局域网 IP。
- ESP32 提供静态页面和 `/api/v1/` API，页面与 API 同源。
- 按键、红外接收器、温度传感器直接连接 ESP32 所在的底板。
- ESP32 通过已核实的驱动电路控制低压直流电机；GPIO 只输出控制信号。
- 供电路径、电机额定电压和驱动型号在 M0 确定，架构图不是接线图。

采用单个固件、单个控制循环。技术路线暂定 Arduino-ESP32 + C++，网页使用原生 HTML/CSS/JavaScript，不引入前端框架。具体工具链版本、板卡标识、红外库和温度库在硬件核对后锁定，不在此时猜测。

## 3. 模块职责与依赖

| 模块 | 负责 | 约束 |
|---|---|---|
| App / 调度 | 初始化、按周期执行输入扫描、温度采样、网络处理和控制 | 不在主循环中使用长时间阻塞等待 |
| BoardProfile | 引脚、电平极性、板卡能力与供电说明 | 未确认引脚不得生成可驱动电机的默认配置 |
| LocalInput | 按键消抖、红外解码和长按过滤 | 输出标准命令，不直接写电机 GPIO |
| WebAdapter | 页面、HTTP 解析、参数校验、状态序列化 | 只调用控制器；不保存另一份设备状态 |
| TemperatureService | 非阻塞采样，检查断线、无效值和过期数据 | 发布有效性与采样时间，不直接开关电机 |
| FanController | 模式切换、温控回差、命令排序、异常策略 | 唯一拥有运行状态、唯一决定电机输出的模块 |
| FanOutput | 将开关要求转换为已验证的驱动电平 | 只接受控制器调用；启动时先设安全关闭状态 |
| StatusIndicator | LED 状态提示 | 读取控制器快照；数码管和蜂鸣器属于后续可选显示 |
| NetworkService | Wi-Fi 连接、重连、IP 输出 | 连接失败不得阻塞本地控制 |
| ConfigStore | 保存温控配置，提供默认值 | 不持久化风扇开启状态或自动模式 |

FanController 不依赖 Wi-Fi、HTTP、红外库或具体 GPIO。硬件和通信变化限制在适配模块内，后续可在电脑上验证控制规则。

所有输入在单个控制循环中串行处理。首版 HTTP 使用与主循环配合的同步处理方式；将来若采用异步回调，回调只能投递有界命令队列，不能直接修改状态。输入洪泛不得饿死温度检查和本地操作。

## 4. 状态模型

所有入口读取同一份 `DeviceState` 快照：

| 字段 | 含义 |
|---|---|
| `bootId` | 本次启动标识，用来区分重启前后的版本 |
| `revision` | 对外状态发生变化时递增的版本 |
| `mode` | `manual` 或 `auto` |
| `fanOutputOn` | 已下发到驱动的开关电平所代表的状态，不代表检测到实际转动 |
| `temperatureC` | 最近一次有效温度；当前无效时为 `null` |
| `sensorStatus` | `initializing`、`ok`、`invalid`、`stale` |
| `sampleAgeMs` | 距离最近有效采样的时间；尚无有效样本时为 `null` |
| `onThresholdC` / `offThresholdC` | 自动模式的开启／关闭阈值 |
| `fault` | `none` 或 `temperature_unavailable`，表示已触发的温控故障 |
| `lastCommandSource` | `button`、`infrared`、`web`、`system` |
| `wifiConnected` | 网络连接状态，不决定电机输出 |

传感器健康状态与控制故障分开：未安装温度传感器时，M4 的手动风扇仍可使用；只有自动运行依赖温度。

### 控制规则

1. 启动先关闭电机，再初始化输入和网络；始终进入手动模式，不恢复上次开启状态。
2. `SetPower(on)` 表示显式开／关，并切换到手动模式。红外优先映射独立开、关命令；单按键切换在控制器内根据当前状态转成一次显式命令。
3. `SetMode(auto)` 仅在传感器样本有效且未过期、阈值合法时接受。进入自动模式先从关闭状态计算：温度达到开启阈值则开启，否则保持关闭。
4. 自动模式中：温度 ≥ 开启阈值时开启；温度 ≤ 关闭阈值时关闭；两者之间保持原输出。默认阈值为 30℃／28℃。
5. `SetMode(manual)` 保持当前输出；若要关闭，使用 `SetPower(false)`。UI 提示模式切换的行为。
6. 自动模式下收到手动开关命令，立即切换到手动并执行该命令。
7. 自动模式中出现无效或过期样本，关闭风扇、转手动并置温控故障。样本恢复后清除当前故障提示，但不自动恢复自动模式。手动模式可以继续开关。
8. 断网保持现有模式与输出，本地按键、红外和温控继续工作；Wi-Fi 后台限频重连。
9. 多来源命令按主循环接收次序处理，最后接受的命令生效。相同显式开关命令重复发送不会再次翻转状态。
10. 同一循环先更新温度健康情况，再处理命令，最后计算自动控制并提交输出，避免在无效温度上接受自动模式。

温度采样设计值为每 1 秒一次，超过 5 秒没有有效样本判为过期；读取需拆分转换请求和完成检查，不能为了等温度转换阻塞输入处理。网页正常连接时每 1 秒读取一次状态。这些是待设备验证的参数，不是实测性能承诺。

## 5. HTTP 接口契约

所有写请求使用 `application/json`；严格校验类型和字段，拒绝跨源写入，不启用开放 CORS。状态响应设置 `Cache-Control: no-store`。参数错误不改变设备状态。

| 方法与路径 | 请求 | 返回／行为 |
|---|---|---|
| `GET /` | 无 | 随固件发布的控制页面 |
| `GET /api/v1/state` | 无 | 完整状态快照 |
| `PUT /api/v1/power` | `{"on":true}` | 切换手动并执行，返回最新状态 |
| `PUT /api/v1/mode` | `{"mode":"auto"}` | 校验前置条件，返回最新状态 |
| `PUT /api/v1/config` | `{"onThresholdC":30,"offThresholdC":28}` | 两个值原子更新并持久化；自动模式立即按新值计算 |

配置默认允许 0～60℃，关闭阈值至少比开启阈值低 1℃。这是桌面实验的产品限制，不是传感器量程。

成功返回 200 与状态快照；格式或范围错误返回 400；温度不可用却请求自动模式返回 409；持久化失败返回 503，保留旧配置。错误体为 `{"error":{"code":"TEMPERATURE_UNAVAILABLE","message":"当前温度不可用"}}` 等稳定结构。

网页每次仅允许一个写请求在途，写操作后刷新状态，不乐观宣称电机已开启。请求超时显示“结果未知，正在同步”，恢复后读取状态；不自动重放过期命令。轮询与写响应以 `bootId`、`revision` 避免旧响应覆盖新状态，检测到重启时重新同步。

首版没有转速或电流反馈，UI 文案使用“控制输出：开／关”，不使用“已检测到风扇转动”。

## 6. 配置与诊断

- Wi-Fi 凭据通过本地私有配置提供，不提交到仓库；串口不打印密码。首版不做配网门户。
- 温控阈值在显式修改且确实变化时写入设备非易失存储，不在采样循环中反复写入。
- 已保存配置包含格式版本，加载时校验；缺失或损坏时回退到 30℃／28℃并记录诊断。
- 串口记录启动、IP、输入命令、模式变化、输出变化及故障；不逐循环刷屏。
- M1～M4 可以不接温度传感器；自动模式接口在该能力缺失时返回冲突错误。

## 8. 实现顺序与后续工单边界

| 里程碑 | 工作边界 | 关键验收 |
|---|---|---|
| M0 硬件核对 | BoardProfile、供电、商家资料与引脚分配 | 未知项明确，电机驱动确认可用 |
| M1 最小程序 | 构建烧录、串口、LED 与按键 | 按键事件可靠、重启正常 |
| M2 本地风扇 | FanController、FanOutput、按键适配 | 默认关闭、消抖、启动电机不重启 |
| M3 红外 | 遥控按键映射与重复帧过滤 | 一次按键只触发一次预期命令 |
| M4 联网 MVP | NetworkService、WebAdapter、网页 | 手机控制与本地状态同步、断网本地可用 |
| M5 温控 | TemperatureService、ConfigStore、自动规则 | 回差、模式切换、无效样本处理 |
| M6 验收 | 控制规则测试、实物故障测试、搭建文档 | 重启关闭、断网继续本地操作、故障不自动重启自动模式 |

规则测试重点：阈值边界与回差、手动覆盖自动、自动模式准入、温度异常与恢复、重复命令、配置拒绝后状态不变。硬件测试重点：供电稳定、真实按键与红外行为、断开传感器、Wi-Fi 中断及恢复、连续运行。

已据此创建 [工单总览](issues/README.md)：25 张必需工单覆盖 M0～M6，包含具体依赖、交付物和验收步骤；7 张后续扩展作为待规划工单。当前为本地 Markdown 工单，尚未同步远程平台；实施状态以工单总览为准。

## 9. 扩展位置

- 调速：确认驱动支持后，扩展控制命令和 FanOutput，不用继电器进行 PWM 调速。
- MQTT：新增通信适配器，复用统一命令和状态快照；届时明确认证、重连及旧指令处理。
- 数码管／蜂鸣器：扩展 StatusIndicator，不增加第二个状态控制器。
- 更多传感器：新增采样模块；业务规则通过控制器明确组合，避免多个模块争抢输出。
- 云端、OTA、多设备：另立后续架构决策，不预先引入服务和抽象框架。
